> 这是一篇操作型示例文档，属于“能力展厅”文档集合，位于 `dev` 分支。它记录的是本次示例站建设时实际采用的步骤，不宣称 `prod` 已完成验收。

内容组织不是“把文章按类型分文件夹”这么简单。一个可读的站点需要先回答：读者从哪里进来、每一步看到什么、下一步去哪里。Folio 的字段只是实现这些路径的工具。

## 第一步：先写读者路径

在新增任何文件之前，先列出至少三条能走通的路径。本次示例站使用了三条：

1. 首页 → 内容组织图谱 → 操作示例文档 → `/showcase` 集合索引；
2. 首页 → 文章集合 → 一篇专题长文 → 相关项目档案；
3. 首页 → 手册集合 → 入门文档 → API 参考 → Frontmatter 参考。

每条路径至少包含三个真实 route，且相邻两步之间必须有可见链接。只在首页放一堆卡片、详情页之间互不相连，不叫组织。

## 第二步：按职责选择类型

| 内容职责 | 选择 | 原因 |
| --- | --- | --- |
| 连续阅读的操作说明 | `doc` | 进入文档壳，有侧边导航与前后篇 |
| 独立观点的长文 | `article` | 按日期排序，自动出现文章 TOC |
| 长期工作的范围记录 | `project` | 独立详情页，不被文档分页吞掉 |
| 参考图谱或索引页 | `page` | 不进入文档壳，但可被集合收录 |

类型写错不会让构建失败，却会让阅读体验变形。例如把操作说明写成 `article`，它就失去了同集合的侧边导航；把项目档案写成 `doc`，它会被塞进手册的上一篇/下一篇序列。

## 第三步：设计文档层级

文档层级由三个字段决定，而不是目录名：

```yaml
type: doc
collection: 能力展厅
section: 操作示例
order: 10
```

- `collection` 决定文档壳最外层的集合；
- `section` 决定集合内部的分组；
- `order` 决定同组内的先后顺序。

本次新增的两篇操作示例使用独立集合“能力展厅”，因此不会打乱既有 26 篇文档的默认导航。这是并行文档治理下比较安全的做法。

## 第四步：补齐日期、作者、标签

`date` 用于文章排序，`tags` 用于搜索摘要，`author` 会进入文章的结构化元数据。示例内容必须显式说明自己是示例，不能伪造真实发布史。

```yaml
date: 2026-11-04
author: Folio 示例内容 · AI Worker
status: dev-sample
```

`status` 当前只是内容字段，不会自动改变构建行为。把 `dev-sample` 写进 Frontmatter，是给维护者的显式信号，不是运行时开关。

## 第五步：验证，而不是假设

完成内容后至少检查四件事：

1. `/showcase` 集合索引是否递归收录了新路径；
2. 文档侧边栏是否只显示“能力展厅”集合；
3. 站内搜索能否命中正文里的 `能力展厅`、`静态构建` 等关键词；
4. 静态构建是否真的写出了对应 HTML，而不是只在 SPA 里可见。
